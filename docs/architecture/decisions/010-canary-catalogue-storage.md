# ADR-010: Canary catalogue — schema bundled, values generated at install, injected at runtime

**Status:** Accepted
**Decision date:** 2026-05-05
**Supersedes:** None — rewritten in place during v0.2 planning. The earlier "JSON file with values bundled in the image" decision was wrong; see *Context* below.

## Context

A canary is a fake credential, URL, or other honeypot string that armor seeds into the agent's context (or expects the agent to never produce). When such a value appears in agent output, an injection has succeeded — the canary acts as a deterministic tripwire that converts a fuzzy semantic problem ("did the model leak something it shouldn't?") into a string-matching problem.

A canary works **only as long as its value is unknown to attackers**. Once a value is published — in a commit, an issue, a Stack Overflow answer, anywhere indexable — it is useless as a tripwire: an attacker reads the public value, instructs the model not to emit *that exact string*, and exfiltrates everything else freely.

The original v0.1 decision (now superseded by this rewrite) treated the catalogue as something to ship in the container image — `src/armor/canaries/default_catalogue.json` was generated by a build-time script and committed to git. That model has a fundamental flaw: **every value committed to a public repo is dead the moment the repo is public.** v0.1 already saw this: an early rotation commit replaced the bundled catalogue after a value leaked through the README and a test spec. The leak repeated through task 031's test spec. Rotation treats the symptom; the disease is "values are committed to the repo at all."

The catalogue must still be:
- Available at daemon startup (immutable for the daemon's lifetime — the active set is snapshotted at boot)
- Validatable (each value matches its `marker_rule` regex)
- Surveyable (operators can list active canary IDs without seeing values)
- Rebuildable (operators can rotate values; per-installation, not globally)

## Decision

**The catalogue is split into two parts: a bundled schema and runtime-injected values.**

### Bundled schema (committed)

`src/armor/canaries/default_catalogue.json` ships **only the schema** — for each canary, the `canary_id`, `kind`, `service`, `marker_rule`, `active`, and `created_at`. The `value` field is **never** present in any committed copy of this file. The bundled catalogue is essentially a list of "shapes" — "we expect to have one AWS-key-shaped canary identified as `aws-key-000`," but never the actual key.

### Runtime-injected values

Values are generated **outside the container, on the host, at install time**, by a generator script that produces a per-installation set. The generator writes the values to a runtime location the daemon reads at boot — typically a mounted file (e.g. `/var/lib/armor/canary-values.json`, mode `0600`) or, for ephemeral test/CI runs, an environment variable carrying a JSON blob. The mechanism is configured by `daemon.canary_values_path` / `ARMOR_CANARY_VALUES_PATH`; details land with task 015.

At boot, the daemon merges the bundled schema with the injected values into the in-memory `CanaryCatalogue`, validates each value against its `marker_rule`, builds the Aho-Corasick automaton, and freezes the active set for the daemon's lifetime. If the values file is missing, malformed, or fails validation, the daemon refuses to start (exit 78).

### Per-installation isolation

Each installation runs the generator independently, so each deployment has a unique value set. A leak of one installation's values has zero blast radius on any other installation. The committed repo, by construction, contains no value that any deployment ever uses.

### Rotation

Rotation = re-run the generator + restart the daemon. Live reload is still out of scope (deferred per the v0.1 decision).

### Tests

Tests must not depend on the bundled file having values. Each test that needs canary values generates an ephemeral catalogue (typically a `tmp_path` fixture) and points the daemon/loader at it. The eval-corpus loader's `{canary:<id>}` references (task 031) resolve against the active catalogue, whatever its source — bundled-plus-injected in production, ephemeral-only in tests.

## Consequences

1. **`src/armor/canaries/default_catalogue.json` reshaped:** Implementation lands with task 015. Until then, the file still contains values (legacy v0.1 shape) and tests load them; this is acknowledged spec drift, scheduled for resolution.

2. **New CLI surface:** `armor canary generate --out <path>` creates a fresh values file. `armor canary regenerate` (was deferred to v0.3 in the prior ADR) is now part of v0.2 / task 015.

3. **New configuration:** `daemon.canary_values_path` (TOML) and `ARMOR_CANARY_VALUES_PATH` (env). Daemon boot fails clearly if the path is unset and `default_catalogue.json` carries no values (i.e. once task 015 ships and the bundled file is reshaped to schema-only).

4. **Test isolation invariant strengthened:** No test uses `Catalogue.load()` against the bundled file for value-matching assertions; tests construct ephemeral catalogues. This is a fitness function (proposed in task 015).

5. **Fitness function:** "No `value` field present in any committed catalogue file" — replaces the v0.1-era "no canary value in committed files outside `default_catalogue.json`" rule. Once the bundled file is values-free, the rule simplifies to "`grep '"value":' src/armor/canaries/*.json` returns no rows."

6. **Forensic log unchanged:** Forensic records still reference `canary_id`, never the value. The "value never in forensic log" rule (codified in `docs/spec/SPEC.md` top-level invariants and behaviors.md B-007) is unrelated to where values live; that rule stands.

7. **Aho-Corasick automaton lifecycle unchanged:** Built once at boot, frozen for daemon lifetime, rebuilt on restart. Only the *source* of the input strings changes.

## Alternatives considered

- **Continue with bundled values + aggressive rotation:** Rotates after every leak. Rejected — leaks happen faster than rotations (v0.1 saw two within a fortnight), and rotation is reactive rather than preventative. The architecture should make leaks impossible-by-construction, not depend on operator vigilance.

- **Generate values inside the container at first boot, persist to a runtime volume:** Almost as good. Rejected because (a) the host is the right boundary — generation at install time is the natural choice for a per-installation secret, mirroring how SSH host keys are generated by `ssh-keygen` outside any container; (b) putting RNG in the daemon-boot path is one more failure mode for boot.

- **Per-tenant catalogues for shared deployments:** Out of scope for v1 (one daemon per session is the target deployment shape). Revisit if multi-tenant becomes a target.

- **Encrypt values at rest in the bundled file with a deploy-time key:** Adds machinery without changing the property that matters. If the key leaks alongside the file, the values are public. Rejected.
